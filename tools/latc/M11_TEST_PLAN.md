# AOT v2 M11 测试计划

## 协议和持久化

- 二进制 batch 的正常、截断、溢出、非法 flag、错误 source 和重复键测试。
- 多进程并发提交同一 source，验证 known 为精确并集且重复提交不启动编译。
- 编译过程中继续提交；第一个 flush 只覆盖屏障序号，第二批随后发布。
- `SIGKILL`、磁盘写入失败、损坏状态和只读缓存后保留最后一个有效清单。

## 单模块增量发布

- 首次和多次增量后，每个 source 均只有一个 `.so`、一个 `.native` 和一个 `.tbset`。
- 新键不在当前模块时，只翻译差集，将结果合入完整 native image，再链接替换模块。
- 新键已在当前模块 TB 表时，不调用编译器或链接器，只原子发布完整 TBSET 和清单；
  模块和 native image 的名称、大小及摘要保持不变。
- 验证目标查找、flag 区分、PC map、signal、fork、dlopen/dlclose 和失效；不得产生
  文件型 JIT TB。
- 运行期间发布新清单，验证下一次进程启动可命中新 TB；损坏模块、native image 或
  清单不得替换旧版本，且 flush 必须返回失败。

## 3A6000 验收

- 使用干净构建和安装目录，记录 commit、build-id、产物 SHA256、CPU 频率和原始日志。
- 约 10 万 TB 分别测完整生成、10% 增量合并和“模块已覆盖”的仅元数据发布；完整
  生成目标不超过 5 秒，10% 增量不超过 2 秒。记录 `flush` 等待时间，不能把应用收集
  时间算成编译时间。
- 使用 1、2、4、8 个翻译线程，验证 TB 键集合和模块结构一致；默认线程数相对已确认
  暖 AOT 基线回退不超过 2%。线程数属于编译选项，不要求不同线程数的文件逐字节相同。
- 分别测开启和关闭 TB 收集的 JIT，回退不得超过 1%。
- Python、Git、SQLite WAL、Redis server/client 先运行收集，再 `flush-all`，随后在不启动
  编译器的只读缓存上严格复跑。要求所有依赖 ELF 文件型 JIT TB 为零、`failed=0`，
  且每个应用暖 AOT 中位数快于 JIT。
